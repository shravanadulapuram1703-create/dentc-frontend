## 1. Purpose and rules

| # | Rule | Consequence |
|---|---|---|
| R1 | **Parity is literal** (AD-8). Every legacy control becomes one parameter, or one member of a parameter, with the same options and the same default. | The mapping is fixed once per signature in `signature_map.json`, and per control where one signature means different things on different reports (`control_overrides`, 15.4). `tools/make_parity_skeleton.py` applies it to all 1,025 controls and `tools/validate_parity.py` proves it per category. |
| R2 | **One parameter model for every report.** A report declares parameters of the 17 types of section 2; nothing else. | No per-report filter code on either side. The generic runner renders any definition (AD-2). |
| R3 | **Same concept, same key; different concept, different key.** | `EXCLUDE RESP. PARTY TYPE`, `EXCLUDE RESPONSIBLE PARTY TYPE` and the Statements row share `exclude_resp_party_type_codes`. Every provider key carries a `provider_role` (3.2), so `provider_ids` and a role key never mean two things on one report. |
| R4 | **A legacy title is not a meaning.** Mapping follows what the control does. | `REPORT TYPE` is `report_format` (Summary / Detail), `report_type` (Lab Report) or `date_basis` (Lab Cost Report); `LAST VISIT DATE RANGE` on Provider Holidays is the holiday date; `CLAIM TYPE` is two different parameters; the PATIENT box is a filter on Audit Trail and the subject of Patient's Notes. |
| R5 | **Enhancements are additive.** They never change a legacy option value, default or meaning. | Added options carry `is_enhancement: true`; a report run with untouched defaults returns the legacy result. |
| R6 | **The server is the authority** (AD-1, AD-7). The browser sends `params` (flat value keys, tokens allowed) with `working_office_id` and, when the report is started from a patient, `context{patient_id}`; the backend validates, resolves tokens, applies rights and stores both `params_input` and the resolved `params` with the run. | Saved views and schedules run without a browser; nothing the form computes is trusted. |
| R7 | **`all` means no predicate**, never an enumerated list; **`none` means an empty exclusion**; a full selection of a checkbox group means what `semantics.full_selection` says (2.5). | A provider added tomorrow is included in a saved `all`; a default run never loses the rows that have no value. |
| R8 | **snake_case** for every key and value (AD-12). Value keys bind directly to backend names. | No mapping layer in the frontend. |
| R9 | **Unknown is stated, not guessed.** A control whose content could not be read is `unknown_legacy`. A dependency nobody observed never disables a control: the rule covers the observed states only, or is written `unknown` (9.2). | Section 11 is the checklist for the live legacy tool. |

Status vocabulary of `signature_map.json` and of the parity files. Signature counts are the mappings of `mappings[]`; control
counts are effective, after `control_overrides`. Every signature is mapped.

| Status | Meaning | Signatures | Controls |
|---|---|---|---|
| `replicated` | Same control, same options, same default | 222 | 435 |
| `replicated_enhanced` | Same options and default plus additive capability (presets, tokens, multi-select, search, extra format) | 102 | 536 |
| `superseded` | Replaced by an equivalent mechanism built into another control (the `SEARCH` and `NONE` buttons) | 9 | 25 |
| `help_text` | Static text or info icon kept as help | 7 | 7 |
| `unknown_legacy` | Role known, content not readable or not confirmed: collapsed static list, clipped row, picker of unknown structure, unconfirmed default rule | 18 | 22 |
| `not_applicable` | Legacy-only technical control with no counterpart | 0 | 0 |

| Step | Action |
|---|---|
| 1 | Run `tools/make_parity_skeleton.py`: every control of the category arrives with status, `param`, `param_type`, `option_map`, default and notes from its signature, and with its `enabled_when` string when it has a rule (9.3, 9.6) |
| 2 | Apply `control_overrides` to the 9 controls of 15.4 (`param`, `param_type`, `option_map`, status, default, notes) and copy `option_enabled_when` for the 9 controls of 9.4. Manual until FLT-22 teaches the skeleton tool both blocks |
| 3 | Fill `report_key`, `phase` and the actions. A control that carries `vendor_doc_options` takes the per-control option map of 11.1 and a status other than `unknown_legacy` |
| 4 | Add the controls that only vendor documentation shows and the hidden parameters of 9.7 (they arrive through `tools/apply_supplement.py` as `.xNN` controls) with the keys fixed there; write `new_behavior` of each dynamic rule from 9.6 and 9.5 |
| 5 | Declare the report parameters: one per parameter of section 15, with the `date_basis` of 7.2, the `scope` fields of 02 (`office_mode`, `office_attribution`, `provider_attribution`), locks (6.4) and report-specific option lists |
| 6 | Never rename or re-type a key of this document inside a catalog. A control that needs another meaning gets a `control_overrides` entry here, so every tool sees it |

## 2. Parameter type system

### 2.1 The 17 types

|---|---|---|---|---|---|---|

default of a member is a boolean (the checkbox state).

### 2.3 Tokens and request context

Notation. In `signature_map.json` (`default_map`, `control_overrides`), in parity files and in this document a token is written as
its bare name. In a report definition, a saved view and a request, `all` and `none` are the reserved strings `"all"` / `"none"`, a
context token is the object `{"token": "<name>"}` (02 section 3.2), a date token is a string inside a date value, and a range
default is a preset (`{"date_preset": "today"}`). In a URL a context token is written `@<name>` (`office_ids=@my_offices`).

| Token | Valid for | Resolves to | Resolved from |
|---|---|---|---|
| `all` | `entity_multi`, `enum_multi` with `accepts_all`, `office_ids`, `office_group_id`, `K_selection` of a `scoped_selection` | No predicate. On the office keys: every office (or office group) the caller may read (6.1) | - |
| `none` | `entity_multi` with `accepts_none` | Empty list: exclude nothing (exclude filters) or include nothing (PAYMENT/ADJ CODES) | - |
| `first_option` | `entity_single` | First row of the option source in its display order, after the `depends_on` filters | option source |
| `working_office` | `office_ids` and its prefixed twins | `[working_office_id]` | `working_office_id` of the request (02 section 4.1); missing: 422 `parameter_required` |
| `my_offices` | `office_ids` | The caller's assigned offices plus the working office - the set of the frontend read mode `my_offices` [V `src/features/office-scope/useReadScope.ts`] | caller profile, `working_office_id` |
| `current_user` | `user_ids` | `[caller]`. Carries the restriction that the legacy tool applies on My Reports without showing a control (9.5); also usable as an ordinary default | caller |
| `current_user_report_provider` | `provider_ids`; display source of `corresponding_provider_id` | `[users.report_access_provider_id]` of the caller (PD-11). Without a link: 403 `report_provider_not_linked` when the value is forced, `all` when it is only the default of a caller who is not restricted | caller profile |
| `current_patient` | `patient_id`, `patient_ids` | The patient in context | `context.patient_id` |
| `current_patient_name` | `patient_name_from`, `patient_name_to` | Sort name `LAST, FIRST` of the patient in context | `context.patient_id` |
| `current_account` | `account_id` | `accounts.id` of the guarantor account of the patient in context | `context.patient_id` |
| `current_responsible_party_name` | `responsible_party_name_from`, `responsible_party_name_to` | Sort name `LAST, FIRST` of the guarantor of that account | `context.patient_id` |
| `office_default_ucr_fee_schedule` | `compare_fee_schedule_id` | UCR fee schedule of the working office (worked example of 02; not a legacy default) | `working_office_id` |
| `today` and the date tokens of 7.4 | `date`, `date_range` | Date in the reference time zone of the run (7.5) | resolved office set |
| `server_value` | default of a `display` parameter and of the statement message texts | Value computed by the server | `display_source` |

A token is resolved only by the server. Two request fields carry the context it needs:

| Request field (run, validate, saved-view resolve, live page; 02 section 13) | Carries | Rule |
|---|---|---|
| `working_office_id` (02) | The office the user works in: `useOfficeScope().office_id` [V] | Body field, never the `X-Office-ID` header (02 C15). Must lie in the caller's allowed office set (6.2) |
| `context{patient_id}` (NEW, requested from 02; request A-1 of 07) | The patient the report is started from. When the runner sends it is owned by 07 (section 4.7): the active patient of `useAuth()` [V `src/contexts/AuthContext.tsx`] when the report is opened from the patient shell. The legacy screens pre-fill from the patient loaded in the session however the report is opened (open decision 14) | Optional. No value: a `current_*` patient token resolves to empty, and a required parameter answers 422 `parameter_required`. A patient the caller may not open: 403 `patient_not_in_office`, the chart rule of 08 S-10 (`assert_patient_visible` [V `app/services/office_scope_service.py`]); the same check applies to a `patient_id` or `account_id` sent as a value. With this field the browser does not substitute the patient itself (the fallback 07 names for a server without it), so `params_input` keeps the token |

| Where a patient-context token is stored | What is stored |
|---|---|
| Report definition default | The token (`{"token": "current_account"}`), so the parity default is testable on the server (FLT-20) |
| Saved view, favorite | The token, never the patient: a favorite of Walkout Report follows the patient in context each time it is opened |
| Run | The token in `params_input`, the resolved id or name in `params` |
| Schedule | Not possible: a definition whose required parameter defaults to a patient-context token is `schedulable: false` (per-record document, 02 section 3.1) |

## 6. Office scope

### 6.1 One parameter, four value keys, no state by absence

The legacy OFFICE/GROUP section (92 reports; LOCATION on one more) is one parameter `office_scope` of type `office_scope`. It
contributes the three value keys named by the brief and by 02 - `office_ids`, `office_group_id`, `all_offices` - and a fourth,
`office_group_ids`. In the form the radio is `office_scope.mode` and the picker is `office_scope.selection`; that pair is form
state and is never sent as such. Every state of the form has an explicit value. A missing key is never a state: it means "use
the definition default", for the form, a saved view, a schedule, a URL and an API caller alike (13.2 action 2).

| `mode` | `selection` | Meaning | `params` sent | Saved view: `office_policy`, `office_scope` (02 section 8.2) |
|---|---|---|---|---|
| `office` | `working_office` | The office the user is working in. Legacy default (box shows the office id, 108 in the captures) | `office_ids: {"token": "working_office"}` | `follow_working_office` |
| `office` | `[108, 112]` | The listed offices (vendor documentation: one or more offices the user can access) | `office_ids: [108, 112]` | `fixed`, `{office_ids: [108, 112]}` |
| `office` | `all` | Legacy `ALL`: every office the caller may read - the tenant for a caller with the view-all right, the allowed offices otherwise. Never an error | `office_ids: "all"` | `fixed`, `{office_ids: "all"}` |
| `office` | `my_offices` | The caller's assigned offices plus the working office (enhancement) | `office_ids: {"token": "my_offices"}` | `assigned_offices` |
| `office_group` | `[4]` | The offices of one office group | `office_group_id: 4` | `fixed`, `{office_group_id: 4}` |
| `office_group` | `[4, 7]` | The union of the offices of several groups | `office_group_ids: [4, 7]` | `fixed`, `{office_group_ids: [4, 7]}` |
| `office_group` | `all` | Every office group: the offices that belong to a group; in a tenant without groups, every office the caller may read (vendor documentation). The default when Office Group is chosen | `office_group_id: "all"` | `fixed`, `{office_group_id: "all"}` |
| - | - | Strict tenant-wide read for API callers, analytics endpoints and drill links. Never sent by the form | `all_offices: true` | `fixed`, `{all_offices: true}` |

| Rule | Detail |
|---|---|
| Exactly one key | More than one of the four keys: 422 `invalid_parameter`, reason `conflicting_office_keys` |
| Absent keys | The parameter takes its definition default (`{"token": "working_office"}` on 91 of 92 reports). Nothing is encoded by absence |
| `"all"` versus `all_offices: true` | `office_ids: "all"` is the legacy ALL: it resolves to what the caller may read and cannot fail for a caller who may read any office. `all_offices: true` keeps the platform meaning [V `require_all_offices`]: tenant-wide, or 403 `office_not_assigned` |
| Several groups | `office_group_ids` resolves to the union of `office_group_office_ids(group)` [V] of each group, intersected with the caller's allowed offices; the criteria echo prints the group names. An office belongs to at most one group (`offices.office_group_id` [V]) |
| `all` in group mode | Offices whose `office_group_id` is set, intersected with the allowed offices; all allowed offices when the tenant defines no group. An office that belongs to no group is not part of a group run [I - the legacy dialog was not captured, 11.2] |
| `my_offices` | Offered to every caller who has assignments; for a caller with the view-all right it narrows the run to their own offices |
| Saved views | `assigned_offices` is the stored form of the token `my_offices`; every other value is `fixed` with the value key as stored, `"all"` included. A view never widens access: `"all"` resolves for whoever opens it |
| Legacy favorites pinned to an office | A saved view that stores the token `working_office` follows the working office (`follow_working_office`); one that stores ids is `fixed` |
| Resolved form | `office_ids: [ids]`, or `null` for a tenant-wide run (02 section 4.1), stored on the run beside the request keys of `params_input` |

### 6.2 Resolution

Who may read which office is the engine office rule of 02 section 4.1 (`app/reports/scope.py`, NEW, ENG-07) and 08 section
4.1; this section fixes how each value of 6.1 resolves against it. The platform resolver is not used: it treats a caller
without any `user_offices` row, and every caller while `OFFICE_SCOPE_ENFORCED` is off, as tenant-wide [V
`OfficeScope.unrestricted()` in `app/services/office_scope_service.py`], which 02 and 08 do not accept for bulk PHI and
financial output. Reused from the platform [V]: `OfficeScope.assigned_ids`, `office_group_office_ids`. Report SQL only ever
sees the resolved office list. "View-all right" below is short for a report-unrestricted caller.

| Caller | Allowed offices |
|---|---|
| Report-unrestricted, as 08 S-3 defines it: a full-access role, or a strict holder of `office_scope_view_all_offices`. The scheduling alias of that code does not count (open decision 13) | Every office of the tenant |
| Has office assignments | The assigned offices |
| No assignment and not report-unrestricted | None: a run that needs an office set is 403 `office_not_assigned` with `details.reason = "no_office_assignment"` (08 S-4). `REPORT_UNGATED_OFFICE_ACCESS` (default off, 02 section 4.1) restores the platform rule for a client whose assignments are not set up yet |

The handler of this document (FLT-03) needs two results of that rule: the allowed office set and the report-unrestricted flag.

| `params` | Resolved | Check |
|---|---|---|
| `office_ids: {"token": "working_office"}` | `[working_office_id]` | `working_office_id` of the request body must lie in the allowed set (403 `office_not_assigned`); missing: 422 `parameter_required` |
| `office_ids: {"token": "my_offices"}` | Assigned offices plus the working office | Empty: 403 `office_not_assigned` |
| `office_ids: [108, 112]` | The list | Each id must be in the allowed set: 403 `office_not_assigned` with `details.office_id`, `details.assigned_office_ids` |
| `office_ids: "all"` | Caller with the view-all right: tenant-wide (`null`). Otherwise the allowed set | Never 403 for a caller who may read an office |
| `office_group_id: 4`, `office_group_ids: [4, 7]` | Offices of the group or groups, intersected with the allowed set | Empty result: 403 `office_not_assigned`, never an empty report |
| `office_group_id: "all"` | Offices that belong to a group, intersected with the allowed set; the allowed set when the tenant has no group | As above |
| `all_offices: true` | Tenant-wide | View-all right required, else 403 `office_not_assigned` |

The resolved office list is printed in the criteria echo. Rows without an office (the "Unassigned office" member of 03 section
5.1) belong to tenant-wide runs only. The analytics endpoints and drill links of 02 keep passing `all_offices`, `office_ids`
(repeated keys) and `office_group_id` as query parameters, as `OfficeScopeDep` reads them [V]; the engine applies the same
allowed-set rule to them.

### 7.4 Relative tokens and presets

```
token  := anchor { ("+" | "-") integer unit }
anchor := today | yesterday | tomorrow
        | start_of_<period> | end_of_<period>
        | start_of_last_<period> | end_of_last_<period>
        | start_of_next_<period> | end_of_next_<period>
period := week | month | quarter | year
unit   := d | w | m | y
```

Offsets apply left to right; month and year arithmetic clamps to the last day of the month. Examples: `today`, `today-30d`,
`start_of_month`, `end_of_last_month`, `start_of_next_month+1y-1d`.

| Week start | Rule |
|---|---|
| Default: `week_start: iso` | The week starts on Monday: the week of `rpt_dates.week_start` (03 section 2.1), of the period rule of 03 section 4.3 and of `reportRange.ts` [V]. It is not an organisation setting, so presets and the weekly columns of the datasets always agree |
| `week_start: payroll` on a definition | The token resolver reads the organisation's payroll week, `time_clock_settings.week_start_day` (one row per tenant, default `sunday` [V `app/db/models/staff.py`]) for `start_of_week`, `end_of_week` and their `last_` / `next_` forms. The two Time Clock reports declare it - `timeClockModel.ts` hard-codes Sunday today [V] - so their presets keep their dates |

Naming rule of the presets: `<period>_to_date` ends today, `this_<period>` is the whole current period, `last_<period>` the
whole previous one.

| Preset (value of `K_preset`) | `K_from` | `K_to` |
|---|---|---|
| `today` (legacy default) | `today` | `today` |
| `yesterday` | `yesterday` | `yesterday` |
| `week_to_date` / `this_week` / `last_week` | `start_of_week` / `start_of_week` / `start_of_last_week` | `today` / `end_of_week` / `end_of_last_week` |
| `last_2_weeks` | `start_of_last_week-1w` | `end_of_last_week` |
| `month_to_date` / `this_month` / `last_month` | `start_of_month` / `start_of_month` / `start_of_last_month` | `today` / `end_of_month` / `end_of_last_month` |

| Rule | Detail |

### 9.1 Expression form

Stored form: the JSON arrays of 02 section 3.2, evaluated by `app/reports/params/expr.py` and its TypeScript twin (ENG-04).
Operands are value keys. This document and the parity files (`enabled_when` in `catalog/*.parity.json`) use an equivalent string
notation; `signature_map.json` carries both for every rule (`enabled_when` or `when`, and `expr`).

```
expr     := and_expr { "or" and_expr }
and_expr := unary { "and" unary }
unary    := "not" unary | "(" expr ")" | "true" | "false" | "unknown" | "ctx." fact | cmp
cmp      := value_key ("==" | "!=" | ">" | ">=" | "<" | "<=") literal
          | value_key ("in" | "not in") "[" literal { "," literal } "]"
          | value_key "contains" literal
          | value_key "is empty" | value_key "is not empty"
literal  := snake_case word | number | "true" | "false"
```

| String notation | Stored form |
|---|---|
| `k == v`, `k != v`, `k > n`, `k >= n`, `k < n`, `k <= n` | `["eq", k, v]`, `["ne", k, v]`, `["gt", k, n]`, `["gte", k, n]`, `["lt", k, n]`, `["lte", k, n]` |
| `k == true`, `k == false` | `["truthy", k]`, `["falsy", k]` |
| `k in [a, b]`, `k not in [a, b]` | `["in", k, ["a", "b"]]`, `["not_in", k, ["a", "b"]]` |
| `k is empty`, `k is not empty` | `["empty", k]`, `["not_empty", k]` (`"all"` is not empty) |
| `x and y`, `x or y`, `not x` | `["and", x, y]`, `["or", x, y]`, `["not", x]` |
| `ctx.multi_office`, `ctx.provider_restricted`, `ctx.user_restricted` | `["ctx", "multi_office"]`, `["ctx", "provider_restricted"]`, `["ctx", "user_restricted"]` (the third fact is requested together with `scope.user_restriction`, 08 UR-1) |
| `k contains v` | `["contains", k, v]` (addition 1) |
| `true`, `false` | `true`, `false` (addition 2) |
| `ctx.feature.<flag>` | `["ctx", "feature.<flag>"]` (addition 3) |
| `unknown` | `["unknown"]` (addition 4) |

Additions to the grammar of 02, requested from ENG-04 (FLT-05 delivers the vectors and the TypeScript side):

| # | Addition | Why |
|---|---|---|
| 1 | `["contains", <value_key>, <literal>]`: true when the list value holds the literal or the value is `"all"` | `in` tests a scalar against a literal list; CHECK TYPE depends on one member of the list `payment_types` |
| 2 | The JSON literals `true` and `false` as expressions | Unconditional `forced_when` (locks of 6.4, restrictions of My Reports), hidden parameters (`visible_when: false`) and display-only controls (`enabled_when: false`) |
| 3 | `ctx` facts `feature.<flag>` for organisation feature flags | Controls that exist only when a feature is switched on (Statements) |
| 4 | `["unknown"]`: evaluates as true. The definition lint (ENG-18, FLT-27) refuses a definition with `status = active` that still contains it | A rule nobody has observed must neither disable a control nor be forgotten (9.2) |

### 9.2 Where expressions attach

Field names of 02 section 3.2; `default_when`, `label_when` and the option-level `visible_when` are additions (13.1).

| Field | On | Effect |
|---|---|---|
| `enabled_when` | parameter | False: the control is greyed and the server replaces the value by `disabled_value` (default: the `default`) before hashing and execution. The form keeps what the user entered, so re-enabling restores it (legacy greyed controls keep showing their value) |
| `enabled_when` | option of an `enum` or `enum_multi` | False: the option is greyed; a stored value that becomes disabled falls back to the default |
| `visible_when` | parameter, or option | False: not rendered; the value is replaced as above (an option: not offered) |
| `required_when` | parameter | True: a missing value is 422 `parameter_required`. Not checked while the parameter is disabled or hidden |
| `forced_when[]: {when, value}` | parameter | Forces the value while the condition holds (REPORT FORMAT on 835 Denial Report with Excel). The form shows the forced value and greys the control - a forced `enum` shows its other options greyed. For a parameter with several value keys `value` is an object of value keys (`{"office_ids": {"token": "working_office"}}`). A different value sent is replaced, not rejected, and reported in `warnings[]` |
| `default_when[]: {when, value}` | parameter | Sets the value once when the condition becomes true; the user may change it (Daily Audit ticks Page Break when grouped by provider). Form-side only: the server never applies it |
| `label_when[]: {when, label}` | parameter or option | Changes the label (Account Balance Over becomes Patient Balance Over) |

| Rule | Detail |
|---|---|
| An unobserved state never removes a filter | `enabled_when` is false only (a) in a state that a capture or vendor documentation shows disabled, or (b) where the driving option itself says that the control does not apply: No Recall Date, "as of today", a date range type that names the other range, an unticked gate (Age Range, Include User in Filters). Every other state nobody saw leaves the control enabled: a wrongly disabled control removes a legacy filter, a wrongly enabled one keeps its neutral default (`all`, `none`, unticked). The tables of 9.3 to 9.6 name those states, and FLT-23 confirms each |
| `unknown` | A control that was captured greyed and whose driver is not known carries `enabled_when: unknown`: it stays enabled, and the lint flags the definition until FLT-23 answers it or the product owner signs a rule off. `false` is reserved for locks and display-only fields |
| Evaluation order | Rules run after scope resolution (13.2), so `ctx` facts exist, and in topological order of the dependency graph, each on the already replaced values. Deposit Slip: Check unticked -> `group_batch_checks` is replaced by `false` -> `batch_check_grouping` is disabled. A forced value wins over a disabled or hidden state |
| `disabled_value` | Stated where the default is not neutral: a greyed `entity_single` whose default is `first_option` (`compare_fee_schedule_id`) declares `null`; greyed range boxes declare `null`; the display-only office scope of Referral Source List declares `{"office_ids": "all"}`; the two hidden parameters of My Daily Journal declare `"all"` (9.5) |
| One source of truth | The validate endpoint returns the disabled value keys in `disabled[]`; the form greys exactly those after each change. It evaluates the same expressions locally for immediate feedback and takes the `ctx` facts from `ctx{}` of the last validate response (13.2) |
| Never an error | A value sent for a disabled, hidden or forced parameter is replaced, so saved views survive definition changes |
| Acyclic | The dependency graph must be acyclic; the definition lint (ENG-18) rejects a cycle |

Evidence vocabulary of 9.3 to 9.7: `shown` = visible in our captures; `documented` = stated or shown in vendor documentation;
`inferred` = deduced from labels and layout; `unknown` = no evidence, confirm on the live tool; `policy` = not a legacy
behaviour: a restriction rule of `08_security_compliance.md`. The tables show the string
notation; the stored form of every expression is in the table of 9.1 and in `signature_map.json`.

### 10.1 Defaults

| Topic | Rule |
|---|---|
| Source | The `default` of each parameter in the report definition equals the legacy default (`default` of the parity file; `default_map` of the signature map turns captured values into tokens, `control_overrides` gives the default of an overridden control directly). A deliberate difference needs `default_differs_reason` (02) |
| Precedence when a report opens | 1. values in the URL; 2. the saved view or favorite being opened; 3. definition defaults |

### 15.3 How the map is produced and checked

| Step | Command | Result |
|---|---|---|
| Generate | generator script holding the rules and tables, reading `legacy/index/signatures.json` and the control index. It asserts section, type and label of every signature id, so a shifted id fails the run; it also asserts that every legacy default of a checkbox group is a legal value, that every expression names declared value keys and that no parameter is mapped twice on one report. Kept outside the repository with the document builder until FLT-22 commits both under `tools/` | `legacy/index/signature_map.json` |
| Validate | `python -I tools/validate_signature_map.py legacy/index/signatures.json legacy/index/signature_map.json` | `SIGMAP VALID` |
| Apply | `python -I tools/make_parity_skeleton.py legacy/index catalog/skeleton` | One pre-filled parity file per category (signature mappings and `enabled_when`; the overrides of 15.4 and the option rules of 9.4 are applied by hand until FLT-22) |
| Prove | `python -I tools/validate_parity.py legacy/index/<category>.controls.json catalog/<category>.parity.json` | `PARITY VALID` per category once report keys, phases and actions are filled |

Blocks of `signature_map.json`:

| Block | Content | Read by |
|---|---|---|
| `meta` | Counts and the conventions for `param`, overrides, rules and tokens | people |
| `mappings[]` | One mapping per signature (358): status, `param`, `param_type`, `option_map`, `default_map`, notes | `validate_signature_map.py`, `make_parity_skeleton.py` |
| `control_overrides{}` | Mapping of one control that replaces the mapping of its signature (15.4) | category authors; the skeleton tool after FLT-22 |
| `enabled_when{}` | Enabling rule per control id with `captured` (`greyed` for 9.3, `enabled` for 9.6), string, stored form, evidence, unobserved states | `make_parity_skeleton.py` |
| `option_enabled_when{}` | Control id -> option value -> rule (9.4) | category authors; the tools after FLT-22 |
| `rules[]` | Visible, required, forced, default and label rules per report (9.5) | category authors |
| `parameters{}` | Every canonical parameter: type, value keys, signature ids, control and report counts, first phase, `options_source`, `provider_role`, `semantics` of checkbox groups | this document (sections 3, 2.5, 15.1) |
| `actions{}` | The criteria-area buttons that become definition actions | category authors |
| `vendor_doc_parameters[]` | Keys for controls that only vendor documentation shows and for hidden parameters (9.7) | category authors |
| `option_sources{}` | Source key -> parameters, reports and the first phase that needs it (13.3) | FLT-06 phase check |
